# Revised meal flow —19November2026

User approved reviewed flow: simulated group→invite bot→host selects actual group members + common zone/mode and starts meal→each selected member individually opts in→private editable preferences review/confirmation→readiness for every selected member→deterministic rank→accept/change requirements/other options→consensus. Group membership and meal participation differ. No real LINE connection.

No overlapping schema/package edits.

Additive contracts frozen:

- CreateSchema accepts optional experience:'chat'. New chat home MUST send it. These rooms start with chat.meal={phase:'setup',selectedMemberIds:[],joinedMemberIds:[]}.
- ChatActionSchema new start_meal:{action:'start_meal',selectedMemberIds:UUID[] 1..5 unique,areaId:'bangkok_demo',mode:'dine_in'|'delivery',expectedPreferenceVersion,expectedRosterVersion}. Host only, bot must invited, room membership open, no finalized mutation. Starts/reset meal selected confirmations only, preserves personal prior preference values as editable drafts. Reconfiguring roster invalidates ranking/acceptances/finalization; selected existing join consent retained where applicable, newlyselected must opt in. First setup nobody automatically joins, even host.
- join_meal:{action:'join_meal',expectedPreferenceVersion,expectedRosterVersion}. Only selected authenticated member, self only. Advances rosterVersion once, clears old snapshot/votes. Repeated new keys no duplicate consent/version bump. Must join before preferences/input/extraction/acceptance. Nonselected group members can chat but their cravings never enter a meal draft/ranking/voting.
- Both actions POST /api/sessions/:id/chat return ChatResponse. Existing message/invite actions remain.
- SessionView.meal?:MealState; ChatState.meal?:MealState. MealState phase setup|collecting, selectedMemberIds,joinedMemberIds. Same canonical object, no separate source. No meal field = legacy room behavior; new UI offers configuring a meal in legacy groups, old /web remains working. New chat rooms enforce gating in backend even if web API is called directly.
- Group SessionView.members stays all group members. Meal participants are active members selected by meal; ranking readiness requires selected roster nonempty, all individually joined AND confirmed, not only those who replied. Votes/finalize denominator = selected active members, never the bot/group bystanders.
- Host explicit reopen remains required before finalized edits/membership changes. Can reconfigure selected roster on open room; prefs of retained participants remain confirmed on roster-only changes (first setup requires reconfirm). Removed member canonical prefs remain private but excluded from ranking/votes. Add/reopen clears all old votes. New joiner confirmation then host rank; no auto rank after roster change.

B pure exports: mealMembers(s:{members:StoredMember[];chat?:ChatState}):StoredMember[]; mealReady(s):boolean (setup false); assertMealParticipant(s,memberId):void typed AppError403 MEAL_NOT_SELECTED /409 MEAL_NOT_JOINED/MEAL_NOT_STARTED.
